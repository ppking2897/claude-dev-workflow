# unit-test — 邏輯需求的單元測試（方法與規範，不綁語言）

這份只講方法與規範。用什麼測試框架、怎麼跑、非同步怎麼控制、fake 放哪，一律從**目標專案現有的測試與建置設定**推（Step 0），不寫死在這裡——寫死的機制會隨專案演進過期，專案本身的 code 不會。

## 核心定位

**測「邏輯」**：輸入 → 狀態／輸出的推導、分支、驗證規則、衍生值、一次性事件（導頁、提示）要不要發出的決策。
**不測 UI**：畫面 render、視覺樣式、導航動作本身 → 實機手測或 UI 測試。

**需求來源**：feature-doc 的 Scenario、PRD 的驗收條件……以專案實際在用的為準。下文的「Scenario」泛指這些，GIVEN/WHEN/THEN 泛指它的前提、動作、預期結果。

## Step 0 — 先摸清這個專案的測試地形

開寫前查清楚下面幾件事。查不到就問使用者，不要猜。

| 要知道的 | 去哪找 |
|---|---|
| 測試放哪、用什麼框架與斷言寫法 | 同一層或相近功能的既有測試檔 |
| 怎麼跑全部、怎麼只跑一支、報告在哪 | 建置設定（`build.gradle.kts`／`pubspec.yaml`／`package.json`…）、CI 設定、專案 CLAUDE.md |
| 非同步與時間怎麼控制 | 既有的非同步測試、共用測試工具（測試用排程器、fake clock、test utils） |
| 現成的 fake／mock／測試資料 | 測試目錄、Fake-First 的產物、fixtures |
| 命名慣例 | 同目錄既有測試 |
| 驗證結果要回寫到哪 | 需求文件的格式（驗證紀錄表、Coverage Matrix…） |

- **模仿既有測試**：框架、斷言風格、命名都跟著現有的走，不要在同一個專案混用兩套。
- **共用測試工具已經有就直接用**，不要另建一支同功能的。
- **專案還沒有任何測試** → 不要空手問，先推一個提案再請使用者確認：
  1. 從建置設定判斷語言／平台，用該生態系的標準測試工具
  2. 找精靈附的範例測試（新專案通常有一支）→ 以它的位置與跑法為起點
  3. 屬於慣例的選擇（手寫 fake 或 mock 套件、斷言寫法、非同步控制工具）→ 列選項加推薦，由使用者決定
  4. 第一支測試順便把共用測試工具（例如非同步控制）放到共用位置，之後的測試才有東西可模仿
  5. 從 code 看不出來的決定（跑法、慣例的選擇）寫進專案 CLAUDE.md
- 查的過程中發現值得記的坑（某個 task 在 Windows 上會被跳過、某個工具的陷阱），提議寫進該專案的 CLAUDE.md，下次就不用重踩。

## 預設順序：test-first（對「合約骨架」寫，不對成品寫）

「邏輯」Scenario **預設先寫測試、再實作**，不是實作完才補。

- 原因：測試**後**寫，容易把現狀（含 bug）拓印成斷言，判官失去獨立性；測試**先**寫，code 還沒做、抄無可抄，獨立性由「時間順序」保證，不靠自律。

**但測試要編譯得過，所以「合約骨架」必須先在**。骨架不是實作，只有形狀：

- 輸入、狀態、事件的型別定義
- 被測單元依賴的抽象介面，以及它的 fake
- 被測單元的空殼：簽名在、邏輯未實作

此時測試**編得過、但會紅**。骨架沒有邏輯可抄，對它寫的測試照樣獨立。

一個 slice 的順序：

```
定 Scenario（標出哪些是「邏輯」）
  → 立合約骨架（型別 + 介面 + fake + 空殼）
  → 本 skill 對骨架寫「邏輯」測試 → 紅
  → 實作邏輯 → 反覆跑到綠
```

> 例外：Scenario 太模糊、要先實作才摸得清形狀 → 退回「實作探索 → 補測試」，但補的時候斷言一律從 Scenario 寫，並且做 mutation 檢查。預設仍是 test-first。

## 測什麼

| 對象 | 測法 |
|---|---|
| 狀態推導 | 送一個輸入／動作 → 斷言狀態 |
| 衍生值 | 同上，斷言由狀態推出來的屬性（例：欄位不合法 → 送出按鈕不可用） |
| 資料層分支 | 讓替身回各種結果 → 斷言上層怎麼處理成功、失敗、空資料 |
| UseCase／商業規則 | 注入替身 → 斷言回傳 |
| 一次性事件 | 斷言「該發時有發、不該發時沒發」，以及內容 |

優先測邏輯最集中的那一層（MVVM／MVI 通常是 ViewModel），其他層視情況。

## Oracle 紀律（測試是判官——別讓它被汙染或變廢）

寫「邏輯」測試時，測試就是判定 code 對不對的判官（oracle）。判官被汙染或是廢的，全綠只是假象。

### 1. 斷言從 Scenario 寫，不准讀 code 反推

expected 一律從 Scenario 的 GIVEN/WHEN/THEN 推。
⛔ 不准「讀被測 code 的現有實作 → 寫個剛好會過的斷言」——那是把現狀（含 bug）拓印下來，綠得沒意義。

> 自檢：把 code 遮住只看 Scenario，你寫得出同一個 expected 嗎？寫不出 = 你在抄 code，不是在驗 code。

### 2. 鎖 oracle——改 code 不改 test

跑「實作 → 測試」迴圈時只改 production code，**不准動測試讓它過**：改 expected 配合現狀、把測試標成跳過、刪斷言、放寬條件，一律禁止。

> 例外：**編譯紅**（fake 缺實作、import 缺）屬於測試基礎設施，可以修測試這一側。**斷言紅不在此列。**

### 3. mutation 檢查——證明測試該紅才紅

每條測試寫完，**故意把它針對的那行邏輯改壞、跑一次、確認真的紅、再改回來**。紅不出來 = 恆真或沒接到目標 = 廢測試 → 重寫斷言。

- 從沒紅過的綠不是證據。
- 只對**關鍵斷言**做（核心狀態推導、分支），不是每一行都改壞一次。
- **變異從 Scenario 推**：逐句看 THEN，每個變異是「違反這句 THEN 的最小改動」，先問「這句 THEN 由哪條測試負責」再動手改。程式漏做的需求沒有那一行可改，只有從 Scenario 出發才碰得到；從剛寫的 code 挑變異，挑到的會是自己的測試本來就擋得住的地方，也會把測試帶向實作細節（有沒有轉圈、送出順序）。
- **反向變異——抓「太嚴」**：上面的正向變異改成違反 Scenario，預期紅；反向變異改成**符合 Scenario、但寫法不同**，預期**維持綠**。反向變異跑紅 = 斷言要求得比需求多 → 審查包標 ⚠️「比需求嚴」，交使用者決定放寬斷言，或把它寫進需求。針對容易寫死的斷言做：整串清單相等（連順序一起鎖）、精確呼叫次數、需求只要求意思卻比對逐字文案。
  > 例：需求「以選取的標籤覆寫」，測試寫死「照點選順序送出」。反向變異改成照清單順序送出——仍符合需求，測試卻紅 → 斷言過嚴。
- **正向變異跑紅只證明測試會叫**；叫得對不對，看審查包的 Scenario 欄。對不到 Scenario 的斷言，變異再紅也是 ⚠️。
- **執行**：一次只改一處、只跑該測試檔、記下哪幾條變紅、跑完確認工作區與執行前一致（例：比對 diff 的雜湊）；結果填進審查包。

> 這是唯一「主動改動 production code 來考測試」的步驟——它驗的不是 code，是測試本身有沒有資格當判官。

### 4. 斷言紅的分流——停給人判 vs 改 code 到綠

| 情境 | 斷言紅代表 | 處理 |
|---|---|---|
| **補測試**（測試後寫、code 已存在） | 需求 ↔ code 漂移 | ⛔ **停**，列出「哪條 Scenario／expected vs actual」交給使用者判斷。不准改 code 去配、也不准改測試去配 |
| **test-first**（測試先寫、code 未實作） | 實作還沒到 | 改 code、反覆跑到綠（oracle 已鎖，見第 2 條） |

> 補測試撞到斷言紅，等於提早發現一次需求與實作不一致——那是使用者的決策點，不要自己消化掉。

### 5. 參照資料取自權威來源——不准自建假清單

如果一條測試同時提供「輸入」和「用來比對的參照」，而這兩者在正式環境本來來自**不同來源**，那條測試**在結構上就驗不到那個接縫**：兩邊都是自己寫的，永遠一致、永遠綠。

```
// ✗ 兩邊都自己寫：測得到演算法，但「清單用字對不對」永遠測不到
輸入 = 定位結果(國家 = "TW", 城市名 = "台北市")
參照 = 城市(代碼 = "TPE", 名稱 = "台北市")

// ✓ 參照從權威來源取：來源的用字一改，比對脫鉤就會紅
參照 = 城市清單來源.取("TW").找(代碼 = "TPE")
輸入 = 定位結果(國家 = "TW", 城市名 = 參照.名稱)
```

適用：地區、幣別、單位、enum 對照表這類**有唯一權威來源**的資料。
極限：這樣驗的是「模組之間用的是同一份來源」；那份來源跟外部系統（API、定位服務）對不對得上，單元測試驗不到，要靠實機或整合測試。

## 產 oracle 審查包（給人審；Scenario 欄先填，mutation 欄最後填）

測試是 AI 寫的、被測 code 也是 AI 寫的 → 同一個人出考卷又寫答案。為了讓使用者審得動（而不是橡皮圖章審整個測試檔），寫完後**產一張對照表**，使用者只審這張：

```
oracle 審查包 — {測試類別或檔案}
| 斷言 | expected | 對應 Scenario 句（原文） | mutation |
|------|----------|--------------------------|----------|
| 送出按鈕可用 | false | THEN 不可送出 | ✓ 改成 true 跑紅 |
| 錯誤訊息     | "帳號不存在" | THEN 顯示「帳號不存在」 | ✓ 改成空值跑紅 |
| 送出的標籤   | 選取的那幾個，不限順序 | THEN 以選取的標籤覆寫 | ✓ 少送一個跑紅；反向：換順序維持綠 |
```

- **先填 Scenario 欄、再挑變異**：每條斷言先對到 Scenario 原句，第 3 條的變異依這一欄逐句推；mutation 欄跑完變異再填
- expected **逐字對 Scenario 原句**（不是對 code）→ 使用者一眼看出斷言有沒有忠實表達需求
- mutation 欄填「故意改壞哪裡 → 確認跑紅」，有做反向變異的接著填「換成什麼等價寫法 → 維持綠」；反向跑紅填 ⚠️「比需求嚴」；沒做的填 ⚠️
- 對應不到任何 Scenario 句的斷言 → 標 ⚠️「無 Scenario 依據」，請使用者確認是多測了還是抄了 code

## 非同步與時間

- **先分清被測路徑是同步還是非同步**。同步的直接呼叫、直接斷言；非同步的必須讓測試能控制排程與時間。
- **測試裡不真的等**：不用 sleep、不靠實際延遲。用專案的虛擬時間／測試排程器推進；要斷言「載入中」這類中間狀態，就推進到一半再斷言。
- **被測路徑寫死在測試控制不到的執行緒或排程器上**，測試推不動 → 讓排程器可以注入，或把斷言挪到同步就觀測得到的點。不要用拉長等待時間來湊。
- **非同步裡丟出的例外可能不會直接讓測試失敗**，或被包在另一個錯誤裡。狀態沒有如預期變化、訊息又看不出原因時，先去找被吞掉或被附帶的例外。
- **一次性事件的管道會不會卡住**，取決於它有沒有緩衝：沒有緩衝時，沒人收就會卡，測試要先開一個收集者。

## 可測性接縫（測不了，通常是架構問題）

被測單元的依賴一路都是**具體實作**（沒有抽象介面），就沒有地方塞替身；具體實作裡又常呼叫平台 API，在測試環境直接炸。

**修法：抽出介面，讓使用端依賴抽象。**

1. 從具體實作抽出介面，只放使用端真的用到的方法
2. 使用端的型別改成介面
3. DI 綁定改成「介面 → 實作」
4. 測試注入 fake，完全不執行實作裡的平台呼叫——問題消失，而不是被遮住

抽介面屬於「修改現有 code」，先照使用者的審批流程提方案。

> ✗ 不要用 band-aid：例如用 try/catch 把平台呼叫的錯誤吞掉、回預設值。那是遮問題，不是解問題。正解是讓測試根本不執行那段。

## Fake 慣例

- **一種行為一個 fake**（成功、失敗、延遲、可切換），比在同一個 fake 裡塞一堆旗標好讀
- 需要斷言「有沒有呼叫／呼叫幾次」時，fake 加計數器（例：缺參數時呼叫次數為 0，證明真的短路、沒打 API）
- 用不到的方法回空值——它只是為了滿足型別，不會被呼叫
- 專案已經有 fake（Fake-First 的產物、共用 fixtures）→ 直接拿來用，不另寫

## 單元測試照不到的地方（要另外驗）

- **DI 設定**：單元測試直接建構被測物件、不經過 DI 容器，所以綁定或參數寫錯，測試全綠也抓不到。改過建構子或 DI 模組後，要實際跑一次 App 進到那個畫面。
- **外部系統的真實值**：API、定位服務實際回什麼，只能靠實機或整合測試。
- **UI 呈現**：見「核心定位」。
- **點擊接線**：ViewModel 測試從送進 Intent 開始，按鈕接到哪個 Intent、點了去哪一頁都在測試之外；畫面測試直接塞狀態、點擊傳空函式時也一樣。這次改到的是接線（按鈕的 onClick、導航的推頁）時，驗證紀錄除了單元測試，還要附實機編號，不能只寫單元測試就標完成。

## 完成檢查

- [ ] Step 0 的地形已查清楚：框架、跑法、非同步控制、現成 fake 都跟著專案既有的做法
- [ ] 斷言從 Scenario 寫（遮住 code 也寫得出），不是抄現有實作
- [ ] 跑「實作 → 測試」時只改 production code，沒動測試去配結果
- [ ] 關鍵斷言做過 mutation：變異從 Scenario 的 THEN 推、確認會紅；容易寫死的斷言另做反向變異、確認維持綠
- [ ] 補測試撞到斷言紅 → 已停下、列出 expected vs actual 給使用者判斷
- [ ] 參照資料取自權威來源，沒有自建假清單
- [ ] 已產出 oracle 審查包
- [ ] **整包**測試跑綠，而且連跑幾輪都綠（不是只跑剛寫的那一支）
- [ ] 驗證結果已回寫需求文件：記到測試方法層級 + mutation 痕跡；沒做 mutation 的不准標完成，改標 ⚠️

## 與其他 skill 的關係

- 專案有產 Scenario 的 skill（feature-doc…）→ 標成「邏輯」的 Scenario 由這份落實成測試
- 專案有核對 skill（verify-feature…）→ 核對時直接跑這些測試拿即時結果
