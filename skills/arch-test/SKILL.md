# arch-test — 把架構規則寫成會紅的測試

寫在文件或 prompt 裡的架構規則，要 AI 剛好讀到、讀對才有用。寫成測試後，不管誰改 code，只要跑測試就會被擋。這個 skill 在專案 repo 裡留下三樣東西：一份架構規則文件、每條規則對應的測試、專案 CLAUDE.md 裡宣告的測試指令。之後由專案自己的測試指令執行：`/my-flow` 第 5 步回歸會跑到，Claude commit 前全域 hook 也會照宣告的指令跑。

這份只講方法；用什麼測試框架、怎麼讀原始碼、怎麼跑，照專案現有的測試與建置設定。各生態系驗證過的做法在 `references/<生態系>.md`（目前有 `kotlin-gradle.md`）。

全程不 commit、不 push；改到建置設定（加測試依賴、測試任務設定）前，先給使用者看要加的內容並等同意。

## 0. 認專案

- 語言、建置工具與測試框架：看建置設定、既有測試的寫法。有對應的 `references/<生態系>.md` 就讀；沒有就照專案現有的測試推出做法，第 3 步證明會紅之後，把做法寫成新的參考檔（只寫實際驗證過的）。
- 測試地形：怎麼跑完整測試、結果檔在哪（以結果檔裡的測試數為準，不看建置成功的字樣）、建置工具會不會因為快取沿用舊結果而沒有真的跑測試。
- 現況：有沒有架構文件（這個 repo 裡的 CLAUDE.md／AGENTS.md 規則段、文件資料夾裡講分層或模組依賴的文件）？有沒有架構測試（測試裡掃 import 或用架構測試套件的）？專案 CLAUDE.md（或 AGENTS.md）有沒有 `架構測試指令：` 那一行？repo 外的上層文件（多專案共用的 CLAUDE.md、外層 rules）只當候選規則的參考，不算這個專案的架構文件。
- 這次要做哪一種：
  - 沒有架構測試 → 從第 1 步走
  - 已有架構測試、要加一條規則（例如 `/my-flow` 第 7 步回饋要補）→ 跳到第 2 步，只處理那一條；已經有宣告那一行就跳過第 4 步的宣告，只做 hook 驗證
- 工作區：`git status` 有未提交的改動 → 建議用 `git worktree add` 另開目錄與新分支，使用者決定。
- 團隊共用的 repo（remote 在團隊的 Git 託管組織、`git log` 有其他作者）：先提醒使用者，加測試檔、測試依賴與宣告那一行要跟團隊說好，使用者確認再往下。remote 在使用者個人帳號、作者只有使用者 → 不用提醒。

完成條件：寫出語言、測試框架、完整測試的指令與結果檔位置、現有架構文件與測試的位置（沒有就寫沒有）、有沒有宣告那一行、讀了哪份參考檔（沒有就寫沒有）、走哪一種、在哪個目錄做。

## 1. 整理架構規則

**舊專案：把現況寫下來，不重新設計。** code 是正本（同 `~/.claude/skills/my-flow/conventions.md`「架構基準」）。

1. 掃建置工具的模組與每個原始碼集合（主程式、測試、各平台專屬的原始碼），列出每一層或每個模組實際依賴了誰。依賴包含 import，以及程式裡直接寫完整名稱的引用。檔案屬於哪一層：語言有套件宣告的（Kotlin、Java）看宣告，不看資料夾，資料夾放錯的檔案以宣告為準；沒有套件宣告的（Dart、TypeScript）看路徑。
2. 畫成 ASCII 依賴圖，標出看起來違反分層方向的邊（例如 core 依賴 feature），每條附檔案位置與數量。
3. 確認每條候選規則是不是已經被編譯或模組邊界擋住：放一個違規的暫時檔，用日常會跑的指令（本機測試指令、CI 的指令）實際編譯，編譯失敗才算擋住，不用推論判斷——只有某個平台的編譯會擋、日常指令照樣通過的情況很常見（例子見參考檔）。擋住的不寫測試，在第 5 步回報的「沒做的」註明擋住它的是什麼；暫時檔刪掉。
4. 列候選規則給使用者挑，一條一列：`規則｜現在有幾處違規｜建議`。0 處違規的規則照樣建議收，當成守住現狀的測試。違規多的也可以收，第 2 步處理現有違規。結構上永久需要的依賴（例：資料庫的總表要登錄每個 feature 的表）→ 建議縮小規則範圍把它排除，不列成例外。現有架構文件寫了、code 卻做不到的規則，列出衝突，由使用者決定。

**新專案：** 有樣板骨架就照樣板的分層；沒有就問使用者分層、狀態管理、導航、DI，每批最多 5 題。

跟規則一起請使用者決定（附推薦）：

- 挑哪幾條規則
- 測試檔要不要也受規則限制（例：presentation 的測試能不能 import data），可以逐條決定
- 規則文件放哪：已有架構文件 → 寫進那份，不另開第二份；沒有 → 照專案的文件慣例（專案 CLAUDE.md 宣告的文件資料夾，例如 `DOC_DIR`；沒有慣例才用 `docs/architecture-rules.md`），並在專案 CLAUDE.md（或 AGENTS.md）加一行指向它
- 用什麼寫（見第 2 步）

每條規則一個編號（`ARCH001`…），寫：規則、為什麼、檢查範圍（主程式、測試）、對應的測試檔與測試名稱。

完成條件：上面四件事都有使用者的決定；確認的每條規則都有編號，並寫進 repo 的那份架構文件。

## 2. 寫測試

一條規則一個測試，測試名稱帶規則編號。

- 規則只看依賴方向（誰 import 誰）→ 用專案原本的測試框架寫一支測試，讀原始碼檔比對，不加依賴。要看型別、繼承、註解、回傳型別這類結構時，才查該語言的架構測試套件：動手前查它的文件確認版本與 API，並確認跟專案鎖定的語言與建置工具版本不衝突。
- 比對兩種引用：import 行，以及程式裡直接寫完整名稱的引用（例：`com.example.feature.x.data.XxxImpl()`）。
- 放在完整測試會跑到、而且讀得到原始碼檔的地方：跑在電腦上的測試，不是跑在手機或模擬器上的。
- 建置工具常因為編譯結果沒變就沿用上次的測試結果，而沒用到的 import 不改變編譯結果，只加一行 import 的違規會被漏掉。把原始碼列為測試的輸入（各生態系寫法見參考檔）。
- 失敗訊息要印在跑測試的終端機上：commit 前的 hook 只轉給 Claude 輸出的最後幾十行，許多測試工具預設只印「N 個失敗」、細節只在報告檔。印不出來就調整測試任務的設定（例：Gradle 的 `testLogging`）。

失敗訊息寫給下一個修 code 的人或 AI 看，每一處違規都要有：

```
ARCH001 core 不得依賴 feature
  core/datamanager/src/main/.../SessionStore.kt:12
  實際：import com.example.feature.login.LoginUiModel
  應該：改依賴 core 裡的 contract，或把這段移到 feature
  規則：<架構文件路徑>#arch001
```

**現有違規**（舊專案才會有）：寫成測試裡的例外清單，每項是「檔案＋被引用的對象」，附原因。例外清單的兩個方向都要檢查：

- 清單外出現新違規 → 紅
- 清單裡某項已經不違規了 → 也紅，訊息寫「請從例外清單刪掉這項」。清單只能變短

例外清單要使用者同意才加。新專案不設例外清單。

完成條件：每條規則都有一個測試，測試名稱帶編號；有例外清單的話，兩個方向都會紅；故意讓一條失敗時，完整測試指令的終端機輸出看得到規則編號與違規的檔案。

## 3. 證明測試會紅

每條規則都做一次（前一條最後的綠可以當下一條的起點綠）：

1. 跑測試 → 綠
2. 在會被這條規則抓到的位置，新增一個暫時檔，引用一個專案裡真的存在的類別 → 跑 → 紅。紅必須是這條測試失敗、訊息指到那個暫時檔；編譯失敗不算，換一個存在的類別重來。至少一個暫時檔只放一行沒用到的 import，確認上面「原始碼列為輸入」有效
3. 刪掉暫時檔 → 跑 → 綠
4. 有例外清單的，兩個方向各做一次：從清單刪掉一項還在違規的 → 紅；在清單加一項不違規的 → 紅，訊息要求刪掉。都改回來

每次跑完確認測試真的執行了：建置工具顯示沿用快取或判定不必重跑時，測試沒有跑，結果不算；用強制重跑的選項重跑（見參考檔），或看測試結果檔的時間是不是這次。

紅不起來 → 測試沒在檢查它宣稱的事，回第 2 步修。

完成條件：每條規則都記下「綠 → 紅（失敗訊息摘要）→ 綠」的實際結果，每一次都是測試真的執行過；有例外清單的兩個方向都記下；暫時檔都已刪除，`git status` 只剩這次要留下的檔案；最後跑一次完整測試，記下測試數與失敗數。

## 4. 宣告指令，驗證 commit 前會擋

全域 hook（`~/.claude/hooks/arch-test-check.py`）在 Claude 執行 `git commit` 前，讀 repo 根目錄的 `CLAUDE.md`、`.claude/CLAUDE.md`、`AGENTS.md`，找到這一行就在 repo 根目錄用 bash 跑反引號裡的指令，結束碼不是 0 就擋下 commit：

```
- 架構測試指令：`<指令>`
```

1. **宣告**：寫進專案 CLAUDE.md 的建置或測試指令段（專案用 AGENTS.md 就寫那裡），一行就好，括號補一句說明。預設宣告完整測試指令：只跑架構測試常會清掉其他測試的結果檔，和完整測試輪流跑時快取也會失效。宣告前跟使用者說清楚：完整測試任何一個沒過都會擋 commit。指令不要用安靜模式，有些工具在安靜模式下不印失敗細節。
2. **驗證**：用假的 hook 輸入在 repo 根目錄跑三次，每次看結束碼：

   ```bash
   printf '{"cwd":"%s","tool_input":{"command":"git commit -m x"}}' "<repo 根目錄>" | py -I ~/.claude/hooks/arch-test-check.py; echo $?
   ```

   乾淨 → 0；放第 3 步那種違規暫時檔 → 2，而且輸出看得到規則編號與暫時檔路徑；刪掉暫時檔 → 0。

全域 hook 不存在時只做宣告，回報寫「commit 前不會自動跑」。

完成條件：宣告那一行在專案的 CLAUDE.md 或 AGENTS.md；hook 驗證三次的結束碼與訊息都記下，暫時檔已刪除。

## 5. 回報

```
架構測試：<專案>（目錄、分支）
規則：ARCH001 <規則>（例外 N 項）、ARCH002 …
文件：<架構文件路徑>
測試：<測試檔路徑>
宣告指令：<指令>（寫在 <檔案>）
證明：ARCH001 綠 → 紅 → 綠 ✓ …；完整測試 <N> 個、失敗 <N>
hook 驗證：乾淨放行 ✓／違規擋下且看得到規則與檔案 ✓／刪掉放行 ✓（或「沒有全域 hook」）
改到的建置設定：<檔案，沒有寫「無」>
參考檔：讀了 <references/…>；新增或補了 <…>（沒有寫「無」）
沒做的：<被編譯擋住的規則與擋住它的是什麼、刻意排除的依賴、CI 沒接、寫不成測試的規則>
```

最後提醒：這些檔案還沒 commit。寫不成測試的規則（要看意思、看畫面才判斷得了的）列在「沒做的」，留在文件裡給審查用。
