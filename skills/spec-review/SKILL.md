# spec-review — 規格對 code 的獨立審查

交付資料夾、規格來源、subagent 分段見 `~/.claude/skills/my-flow/conventions.md`。

reviewer 的價值在於看不到作者怎麼想：它只拿規格和 code，自己找反例。

## 步驟

1. **固定範圍**：只審已提交的內容。比較基準預設 `git merge-base <主線> HEAD`（主線看專案 CLAUDE.md，沒寫就問使用者）。`git status --porcelain` 有未提交改動或未追蹤的檔案 → 列給使用者，請他授權 commit，不自行 commit；不該進 repo 的檔案由使用者排除，記在 `spec-review.md` 的「排除」那行。commit 只在本機：不 push、不開 MR、不 rebase。記下受審 commit 的完整 SHA。審查期間不再改 code。
2. **準備輸入**：這次相關的規格段落；架構基準（feature-doc 技術設計裡寫明照哪個既有實作的那段；沒寫就給「無」）；diff（新檔讀全文）；`device-check.md`（審查開始時已經有才給）。交付文件、實作對話、作者摘要都留在主對話。跟 `/device-check` 同時跑時，實機抓到的問題等審查回來後併進第 6 步一起修、一起複查。
3. **分段**：照共用約定分成 1～5 段，列一行給使用者看（段名＋包含哪些需求），接著直接開始。
4. **派 subagent**：每段一個，全新、唯讀、背景執行，effort 設 `xhigh`，指示用下面的範本。
5. **處置**：收齊後去重；逐條讀 source 確認，分成「要修」「要問使用者」「不成立（附理由）」三類；「要問使用者」的記進「使用者決策」，標「待決定」。「規格沒寫的行為」讀 source 確認 code 真的這樣做後，列給使用者選：補規格（照 `/my-flow` 第 2 步「先改規格文件、給使用者確認，再改 code」）、改 code、或先不處理。選了就算處置完成，「先不處理」也算。
6. **修正與複查**：修完範圍內的（含實機抓到的），請使用者授權 commit。修正一律是新的 commit，不 amend、不 rebase，保留清楚的審查與修正歷程。用 SendMessage 請**同一個** subagent 看 `<受審 commit>..<修正 commit>` 的全部改動與直接受影響的行為。實機抓到的問題，修完另外重跑 `/device-check`（原本失敗的情境，以及修正直接影響的其他情境）；這裡的複查只看 code，不算實機重驗。複查最多 3 輪，第 3 輪還有必修就停下來交給使用者（見共用約定「subagent 分段」）。
7. **寫 `spec-review.md`**，在檢查紀錄加一列。必修／應修／可選的數量從發現表的嚴重度欄重數，「花多久」用 subagent 派出與回報的時間算，不憑印象填；沒有時間來源就寫「沒記」。

完成條件：每條發現都有處置與依據；必修項全部修完並經同一位複查閉合，或在「使用者決策」標「已同意保留」並附理由（標「待決定」的還不算完成）；第一行的閉合 commit 是最後一次複查看過的 commit（沒有修正就等於受審 commit）。

## subagent 指示範本

```
你是獨立 reviewer，唯讀：不改任何檔案，不再派 subagent。
你的範圍：<段名>。其他段（不歸你）：<段名清單>。
規格：<路徑，或貼上這段的 Requirement／Scenario>
架構基準：<規劃文件裡照哪個既有實作的那段，或「無」>
改動：<基準>..<受審 commit> 的 diff；新檔請讀全文：<檔案清單>
實機結果：<device-check.md 路徑，或「無」>

逐條情境檢查：
- code 的行為跟規格不一樣的地方
- 測試沒有真的驗到情境：把那段邏輯刪掉，測試還是會過
- 邊界：斷線或逾時、重複點擊、切背景再回來、返回、登入失效
- 跟其他段的交界：資料或狀態交過去之後還成立嗎
- 寫法跟架構基準不一樣：分層、狀態管理、導航、DI；去讀基準指的既有實作來比。命名與排版不在範圍

反過來，從改動往規格查（只看這次 diff 新增或改到的，不掃整個專案）：
- 列出改動裡的行為進入點：ViewModel／UseCase 的 public 方法、每個 Action／Event、每個導航分支、對錯誤碼或回應狀態的分支
- 每一個問：規格有情境描述它嗎？沒有 → 列進「規格沒寫的行為」，附 檔案:行號 與它實際做了什麼
- 不判對錯：可能是規格漏寫，也可能是 code 多做了。只負責讓它被看見

輸出：必修／應修／可選，每條附 檔案:行號、對應情境、怎麼重現、建議修法。
「規格沒寫的行為」另列一類，不分嚴重度。
沒問題的情境各列一行「已檢查」。
```

## `spec-review.md` 格式

```
產生：<時間> @ <閉合 commit>；基準 <base>；受審 <受審 commit 完整 SHA>
排除：<使用者排除、不進 repo 的檔案，或「無」>
分段：<段名：需求清單>

| # | 嚴重度 | 段 | 情境 | 問題 | 處置 | 依據 | 複查 |
|---|---|---|---|---|---|---|---|

## 規格沒寫的行為
| # | 段 | 檔案:行號 | 實際做了什麼 | 使用者選擇（補規格／改 code／先不處理） |
|---|---|---|---|---|

## 使用者決策
| # | 項目 | 狀態（待決定／已同意保留） | 理由 | 日期 |
|---|---|---|---|---|

## 檢查紀錄
| 日期 | 範圍 | 花多久 | 必修 | 應修 | 可選 | 規格沒寫 |
|---|---|---|---|---|---|---|
```
