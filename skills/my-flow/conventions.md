# 個人流程共用約定

`/my-flow`、`/device-check`、`/spec-review`、`/delivery-doc` 共用，`/arch-test` 引用「架構基準」。改這裡會改到這些 skill 的行為。

## 交付資料夾

- 位置：`<repo 根目錄的上一層>/<主題>/`。repo 根目錄用 `git rev-parse --show-toplevel` 取得；主題是 feature-doc 的檔名（不含 `.md`）。不在專案 repo 內、不進版控（個人專案的上一層雖然也是 git repo，但 `.gitignore` 預設全部忽略）。
- 內容：

  | 檔案 | 誰寫 |
  |---|---|
  | `device-check.md`、`device/`（實機截圖）、`target/`（要實現的畫面） | `/device-check` |
  | `spec-review.md` | `/spec-review` |
  | `regression.md`、`baseline/`（基線的測試結果與 lint 報告） | `/my-flow` 第 5 步回歸，格式見下方「回歸紀錄」 |
  | `<主題>.html` | `/delivery-doc`（圖片直接引用 `device/`、`target/`） |
  | `to-questionnaire-*.md`（給 PM／後端的問卷） | `to-questionnaire`。它預設存在目前資料夾，叫它時請它存到這裡；`/my-flow` 找問卷時交付資料夾和 repo 根目錄都看 |

- 每個檔案第一行：`產生：<時間> @ <git rev-parse --short HEAD>（未提交改動：有／無）`。`/my-flow` 用它判斷有沒有過期。
- 每個檢查在自己檔案最後的「檢查紀錄」表加一列：日期、範圍、花多久（開始到結束）、抓到幾項（依嚴重度）。`/delivery-doc` 彙整這些列，用來看哪個檢查值得留。

## 回歸紀錄

回歸是確認這次的改動沒有弄壞原本會動的東西：跑專案的靜態檢查＋完整測試，跟基線（這次改動開始前的 commit）比，只看多出來的問題。

- **比哪兩個版本**：基線是 `git merge-base HEAD <目標分支>` 算出的 commit（目標分支＝這次 MR 要合進去的分支，例如 `develop`；不確定就問使用者）。現在是工作區，包含還沒 commit 的改動與未追蹤的新檔。
- **基線**：在暫時的 detached worktree 跑同一組指令。移除 worktree 前，把各模組的測試結果（要有個別測試結果的報告，例如 JUnit XML）與 lint 報告複製到交付資料夾 `baseline/`，並在 `regression.md`「跑了什麼」記下基線的 commit 完整 SHA、執行的指令、建置環境（JDK、Gradle wrapper、依賴版本）。之後重跑回歸（例如中途又改了 code）直接拿它比，不重建基線。只有基線本身的條件變了才重建：比較基準換了（例如主線合進來後 merge-base 變了），或這次執行的指令、建置環境跟基線記的不同。功能分支往前 commit，本來就跟基線不同，不算。
- **`regression.md`** 依序寫：
  1. 結論：一句話，通過、哪裡退步，或哪裡無法判定
  2. 跑了什麼：指令、現在與基線各花多久；基線的 commit、指令、建置環境
  3. 單元測試：各模組的測試數／失敗數，基線 vs 現在；失敗的測試用「模組＋測試類別＋測試名稱」比，分成新增失敗、原有失敗、已修復，只有新增失敗算退步。報告沒有個別測試結果、比不出來時寫「無法判定」，不當成沒有退步
  4. lint：各模組的數量，以及新增、消失的項目（用嚴重度、規則、檔案、訊息比，不看行號）；新增的每項附處置
  5. 靜態檢查：含專案自己的架構測試，沒有就寫「這個專案沒有架構檢查」，並在結尾建議用 `/arch-test` 建立
  6. 沒跑的與原因，每項附處置
  7. 檢查紀錄（照上方「交付資料夾」的約定，每跑一次加一列）

## 規格來源

| 工作目標 | 規格（判對錯的基準） | 進度 | 組 |
|---|---|---|---|
| feature-doc | `{DOC_DIR}/<Feature>.md` 的「行為規格」「技術設計」（`DOC_DIR` 見專案 CLAUDE.md 的「Skill 配置」，預設 `.claude/docs/`） | 同檔「實作計畫 + 驗證紀錄」 | Slice，組號寫成 `Slice <N>`（例：`/device-check Slice 3`） |

文中的「情境」指 `#### Scenario:`。

「組」是一次做完、一次測的一塊，規劃時照這樣切：

- 按功能切，每組從資料做到畫面，做完就能照情境走。不按分層切（資料庫一組、Repository 一組、畫面一組），不然高風險組做完沒有畫面可以上手機驗。
- 每組列出涵蓋的情境名稱：寫在 feature-doc Slice 的驗證紀錄表。`/device-check <組號>` 走的就是這份清單。

「專案 CLAUDE.md」指 repo 根目錄的 `CLAUDE.md`；專案規定根目錄只能匯入 `AGENTS.md` 時，指 `.claude/CLAUDE.md`。等待標記、`DOC_DIR` 等 Skill 配置都寫在這一份。

`/unit-test` 的改壞結果（oracle 審查包）：在 feature-doc 驗證紀錄表的「驗證方式」欄。沒有就當作這次沒有改壞紀錄。

## 架構基準

判斷 code 該怎麼寫，基準是 code 現在的架構。

- 找同一個模組裡同類的既有實作（同一種頁面、同一層的 Repository），照它的分層、狀態管理、導航、DI 寫法做。規劃時在規劃文件寫明照哪個既有實作（檔案或資料夾）。
- 新專案還沒有既有實作時，以建專案用的樣板骨架為準，第一個功能做完就成為之後的既有實作；沒用樣板時，規劃第一個功能時跟使用者定好分層、狀態管理、導航、DI，寫進規劃文件。
- 新舊寫法並存（例如 MVVM 與 MVI）時，照這次改動所在模組的寫法；模組裡也混著兩種時，列出兩種寫法讓使用者選。
- 專案寫好的文字規則只當參考：跟 code 現況一致才用；不一致時照 code，把衝突列給使用者，規則不自己改。
- 專案的 AGENTS.md／CLAUDE.md 明寫新 code 要照規則、不照舊 code 時，照專案的規定。
- 專案規則會讓某一步明顯多做很多事時，動手前跟使用者說會照哪條規則、多做哪些事，有實測時間就附上，讓使用者決定照做或簡化。

## 高風險組

改到下列任一項的組：換頁或返回、App 切背景再回前景、登入狀態或存起來的資料、付款、跟後端之間的資料格式。

哪幾組是高風險組，在第 1 步規劃時標在每一組（feature-doc 的 Slice）：`高風險：是（<對到哪幾項>）` 或 `高風險：否`，跟規劃一起給使用者確認。之後第 3 步要不要跑、能不能跳過，都照這一行判斷。

## subagent 分段

- 審查或核對依內容分段，同時最多 5 個 subagent。
- 分段單位是彼此獨立的區塊：不同功能、不同畫面、不同資料流。
- **連貫性**：一條行為跨好幾個區塊時（例如「登入 → 首頁 → 按返回」「登入失效 → 換頁」），整條交給同一個 subagent。只有一個區塊、或全部連在一起時，就只派 1 個。
- 每個 subagent 拿到：自己那段的規格與相關檔案、其他段的名稱（知道邊界在哪）、唯讀的指示。
- 主對話收齊後去重，逐條讀 source 確認是真的再處置。
- **複查最多 3 輪**：修完請同一個 subagent 看一次算一輪，每個 subagent 各自計數。第 3 輪看完還有沒閉合的項目（審查的必修、核對的不一致），就不再修、不送第 4 輪，停下來列給使用者：還剩哪幾條、每輪各修了什麼、為什麼沒收斂（修 A 壞 B、對規格理解不同、reviewer 標準在變），附建議（改規格、換做法、同意保留）。使用者決定後的修正重新從第 1 輪算。不收斂多半不是修得不夠，是前提有問題，再修一輪通常只是換個地方錯。

## 回饋候選清單

第 7 步收尾用來記「這類問題發生過幾次」的清單。位置看「Skill 配置」的 `FEEDBACK_LOG`：先找專案 CLAUDE.md，再找全域 `~/.claude/CLAUDE.md`，都沒寫才用 `.claude/docs/feedback-candidates.md`。每列至少有：類別、來源（專案／工作主題／來源報告 #發現編號／首次發現的檢查時間或輪次）、狀態（候選／已補：寫在哪）、驗證（已驗證／待驗證）。
