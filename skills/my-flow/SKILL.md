# my-flow — 個人開發流程導覽

預設只做兩件事：說明流程，判斷現在在第幾步並給出下一個要叫的指令。使用者說「繼續流程」時，才接著叫下一步（見最後一節）。

交付資料夾、規格來源、高風險組的定義見 `~/.claude/skills/my-flow/conventions.md`。

## 流程

每一步分三種事：**做**（產出東西）、**審**（找問題）、**點**（列出現在的狀態，不判對錯）。

```
步驟              做（產出）              審（找問題）                    點（列狀態）
1 規劃            spec 或 feature-doc、   grilling（把沒定的決策問清楚）
                  給 PM／後端的問卷、
                  架構基準（照哪個既有實作）
2 實作＋測試      code、測試              /unit-test（關鍵斷言故意改壞）
3 高風險組實機                            /device-check <組號>
4 審查＋全部實機                          /spec-review ＋ /device-check
5 回歸                                    靜態檢查（含架構檢查）＋完整測試，跟基線比
6 交付文件        HTML                    subagent 核對 HTML              /blocked → 第 8 段
7 收尾            回饋規則、MR、          /verify-feature
每一步                                                                    /my-flow：進度＋提醒
```

各步細節：

1. **規劃**（開始一個功能時）
   - 設計討論收斂 → `/feature-doc`
   - 使用者或 App 能決定、還沒定的決策 → `grilling`（「繼續流程」時這裡直接叫；使用者也可以自己打 grill-me）
   - 只有 PM／後端能答的題 → `/mattpocock-skills:to-questionnaire`（只能使用者打，這裡提醒）。需求一對齊完就出問卷，不等開發做完；開發先用暫定答案，標專案宣告的等待標記。答案回來後照「問卷答案回來時」一節處理。暫定答案依情境定義的程度分兩種寫：
     - 整條情境沒定義（TODO 情境）：情境維持 TODO、狀態 ⏸️，不寫測試；暫定答案寫在技術設計與 code 的等待標記
     - 已定義的情境裡有一個細節等外部：照暫定答案寫進情境並測試，情境行尾註明「（暫定，等 PM：待辦『<項目>』）」
   - **題名發現當下就定死**：在待辦表取一個固定題名，之後不改字；code 的等待標記（題目與移除條件）、情境的「暫定」、問卷題目都原字照抄。題名不一致，答案回來時用題名搜會漏。字串檔、設定檔這類非 code 檔也加標記（XML 用 `<!-- -->`），一批字串在段落開頭標一處；真的沒地方標的，待辦表註明「無程式標記」。Claude 執行 `git commit` 前，使用者層 hook `~/.claude/hooks/todo-title-check.py` 會對照 `TODO(等PM)` 標記的題名與 `.claude/docs/*.md` 的待辦表，只提醒、不擋；其他寫法的等待標記（例如 `TODO(等外部)`）不在它的範圍，要自己對
   - 使用者決定先不問的題：在 `/my-flow` 讀得到的地方（feature-doc 待辦表的該列）註明「延後：<原因>；再問：<條件>」，例如「延後：其他畫面還在調；再問：畫面定稿時」。沒講再問條件就問使用者；預設最晚在進第 4 步前再問一次
   - 每條情境標好怎麼驗：單元測試或實機
   - 每個畫面對一次這 5 種狀態：空清單、錯誤、載入中、長文字、系統大字體。規格有情境或 Figma 有畫的照做；兩邊都沒有、畫面又會出現的，列進給 PM 的問卷，不自己決定長相
   - 分組照共用約定「規格來源」的切法：按功能切，每組列出涵蓋的情境
   - 每組標好「高風險：是（原因）／否」，跟規劃一起給使用者確認（見共用約定「高風險組」）
   - 高風險組在確認時逐條列出情境：每條碰到哪個高風險項、要不要上手機（例：「登入成功 → 進入首頁｜換頁、登入狀態｜要」「密碼少於 8 碼 → 顯示錯誤｜無｜不用」），請使用者補漏或剔除，例如平常想不到的「登入中切背景」。確認後的「要」就是這組 `/device-check` 要走的情境，做完沒有實機證據不能標完成
   - 寫明架構基準：照哪個既有實作做（見共用約定「架構基準」）
   - 專案有現況索引（第 7 步補出來的那種）時，查現況先看它；它跟 code 對不上就照 code，並把對不上的那幾列列進這次第 7 步要更新的項目
   - 專案沒有架構測試：提醒使用者可以先跑 `/arch-test` 建立，使用者決定；不建也照常往下
   - 讀回饋候選清單（見共用約定「回饋候選清單」）「驗證」欄寫「待驗證」的列，這次功能會碰到那個情境的，列進提醒段，做到那裡時順便確認規則有沒有生效
2. **實作＋測試**（每組）：立合約骨架（型別、介面、fake、空殼）→ `/unit-test` 對骨架寫邏輯測試，先紅 → 實作到綠 → 故意改壞。實作中發現規格要改：先改 feature-doc（行為改了標 MODIFIED），給使用者確認，再改 code；技術設計跟 code 對不上就當下更正
3. **高風險組實機**（標了高風險的組一做完，而且後面還有這次要做的組）：`/device-check <組號>`，只走這組的情境。最後一組是高風險組時跳過，第 4 步的全部實機會涵蓋它
4. **審查＋全部實機**（全部組做完）：`/spec-review`（背景）＋ `/device-check`（全部情境）同時跑。審查開始時還沒有實機結果；實機抓到的問題併進修正，修正（審查＋實機的）→ 同一位 reviewer 複查 code；實機失敗的修好後另外重跑 `/device-check`，走原本失敗的情境，以及修正直接影響的其他情境（找法同「問卷答案回來時」第 1 步）。reviewer 複查不算實機重驗。審查與實機都回來後，`device-check.md` 的畫面差異與數值差異也逐條處置（要修／要問使用者／保留附理由），跟審查發現一起列給使用者
   - 通過條件：審查必修閉合；`device-check.md` 涵蓋全部情境（只跑過單組的不算）；這一步發現的每個問題（審查發現、實機失敗或無法驗的情境、畫面與數值差異）處置已完成，也就是修正後重驗通過；已讀 source 核對確認不成立，附具體依據（`spec-review.md` 處置欄的「不成立」）；或使用者明確同意保留並附理由（記在 `spec-review.md`「使用者決策」，標「已同意保留」）。寫「預計修正」或標「待決定」的還沒完成，留在第 4 步。規劃時就用暫定答案、等 PM／後端的項目不受這條限制，照提醒段處理
5. **回歸**：先把 feature-doc 待辦表裡屬於 App、不等外部的項目列給使用者，問要不要在回歸前做。接著跑專案的靜態檢查＋完整測試，跟基線比，結果寫進 `regression.md`、基線報告存到 `baseline/`（定義與格式見共用約定「回歸紀錄」）
   - 通過條件：`regression.md` 有結論；必要檢查（靜態檢查＋完整測試）都跑完；沒有新增退步。例外（沒跑的檢查、新增失敗、新增 lint、無法判定）每項都經使用者明確同意保留並附理由，記在 `regression.md` 該項的處置，才算通過。其他情況留在第 5 步
6. **交付文件**：`/delivery-doc`，內部依序 ① 點：`/blocked` 清點還卡著的事 → ② 做：寫 HTML 八段，第 8 段放 ① 的結果 → ③ 審：subagent 核對 HTML 跟 code、截圖、審查結果
7. **收尾**：
   - **回饋**：`spec-review.md`、`device-check.md` 這次抓到的問題，以及 `regression.md` 的新增失敗與新增 lint，逐條判斷要不要變成更前面的規則。「同一類」看原因、不看症狀（圖示變色和圖片被裁切，原因都是「Figma 匯出的圖不等於設計稿」）
     - 規劃時為了查同一類現況翻了很多檔（某頁打哪些 API、某流程經過哪幾頁、某資料存在哪），也算一條發現，照下面同樣的規則判斷。「同一類」看問題的種類，不看是哪個功能：做相簿頁查「這頁打哪些 API」、下個月做地圖頁又查一次，就是第二次
       - 要補時，補的是那個專案的**現況索引**，只建這一類的一份（例如只建 API 對照）。每列只寫指向哪個檔或符號，不抄 response 欄位或流程細節，降低過期風險
       - 位置：專案有文件分工規定的照它的規定；沒有的跟使用者定。索引在專案 repo 裡，給使用者確認後跟這次的 MR 一起送
       - 已經有現況索引的專案：這次改動新增或改到索引涵蓋的範圍（新頁面、新 API 呼叫處），在這裡順便更新那幾列，跟第 1 步發現對不上的列一起改
     - 確定會再撞（環境或工具固定的坑），或漏掉代價高（錢、資料遺失、登入或隱私）→ 第一次就補
     - 其他 → 查回饋候選清單，先比「來源」（專案／工作主題／來源報告 #發現編號／首次發現的檢查時間或輪次）：
       - 這次的發現已經記過 → 同一次發現重跑收尾，只更新原紀錄，不算再發生
       - 同一個還沒解決的問題，後續重驗仍失敗（報告裡換了新編號也一樣）→ 沿用原事件的來源，只更新紀錄，不算再發生
       - 同一類、另一個獨立事件（同一主題的不同事件也算）→ 這是第二次，補成規則；那一列加上這次的來源，標「已補：寫在哪」
       - 沒有同類 → 新增一列「候選」，附來源
       - 同類那一列的來源是「待確認」→ 不當成第二次的依據，問使用者是不是同一次
     - 那一列已標「已補」又發生 → 先確認事件發生時那條規則已經在（規則的 git 紀錄或補上的日期早於事件）；早於事件才算規則沒生效，查原因（沒被讀到、寫得不夠具體、放錯步驟），提修正建議給使用者確認，不另外新增規則。事件早於規則就只記來源。兩種情況這次的來源都加進那一列
     - 要補時照下面順序選位置，給使用者看「補什麼、補在哪、判斷理由」，確認再寫：
       1. 能用程式判斷的 → 測試或 lint；架構類（依賴方向、模組或檔案放錯層）用 `/arch-test` 加一條架構測試
       2. 某個步驟固定要檢查的事 → 那個 skill 的檢查項
       3. 其他文字規則 → 全域 `~/.claude/CLAUDE.md`
       - 專案 repo、多專案共用層的 CLAUDE.md 不自動寫：覺得放那裡比較合適時，在建議裡提醒使用者，由使用者決定要不要自己加
       - 專案有自己的規則演進流程 → 寫進專案的規則照它的流程走
       - 寫進專案 repo 的（測試、lint）跟這次的 MR 一起送
     - 補完驗證：這次補的規則都補完後，開一個新的 session 或 subagent，把各條規則原本出事的情境分開交給它，不給預期結論，看它有沒有讀到新規則、有沒有照做。沒照做 → 規則再改，同一輪重驗。結果寫進回饋候選的「驗證」欄：通過寫「已驗證：<日期>、怎麼驗」；要上手機或長時間準備、subagent 重現不了的寫「待驗證：<下次碰到什麼情境時驗>」
     - 這次功能碰到了「待驗證」的情境（第 1 步列過的，或做的過程中遇到的）→ 規則有生效就改成「已驗證」；沒生效照上面「已補又發生」處理
   - 合併、解完衝突後 `/verify-feature`；接著開 MR

## 第 4 步之後又改 code

觸發：第 4 步的審查已經閉合，又為了其他原因改 code（例如補素材、追加小需求）。問卷答案回來而改 code 的，走下一節「問卷答案回來時」。

- 改到行為（State、Action、ViewModel、資料、導航）→ 派一位新的 reviewer（照 `/spec-review` 的指示範本，effort 設 `xhigh`），只給規格與這次的改動（先請使用者授權 commit，範圍是 `<閉合 commit>..<新 commit>`）
- 改到畫面，或碰到高風險項（共用約定「高風險組」列的那幾類）→ `/device-check`，走受影響的情境，參數帶情境名稱
- 一律重跑第 5 步回歸；在 `spec-review.md` 記一行：審查閉合後改了什麼、跑了哪些；交付文件已經產出的，重跑第 6 步

上面三條各自判斷，可以同時成立，審查和實機互相不能替代。

完成條件：上面該重跑的都有新結果，而且第 4、5 步的通過條件仍成立。

## 問卷答案回來時

觸發：使用者說某題答案回來了，或問卷檔裡那題已經填了答案、code 裡還留著它的等待標記。

1. **找範圍**：從那題對到受影響的地方：行尾註明「暫定」、指到這題的情境與它同名的測試；用這題暫定答案的 TODO 情境；code 裡它的等待標記（`/blocked` 列得出來）。完成條件：受影響的情境、測試、等待標記都列出，各附檔案位置。
2. **比對暫定答案**（TODO 情境不論答案一不一樣，都補完 GIVEN／WHEN／THEN，照第 2 步先寫測試，再拿掉 TODO 與等待標記）：
   - **跟暫定一樣** → 拿掉等待標記；情境或待辦表寫「暫定」的地方改成定案。測試本來就照這個答案寫，不用重測。
   - **跟暫定不同** → 需求改了，受影響的部分從第 2 步重走：
     1. 改情境，變更紀錄標 MODIFIED（PREVIOUSLY／CHANGE）
     2. 改測試的預期值：先給使用者看「舊 expected 對新答案」的對照表，同意才改。需求變了才動測試，這跟 `/unit-test` 的鎖 oracle 不衝突
     3. 測試先紅 → 改 code 到綠 → 對改到的斷言做突變
     4. 有畫面、或屬於高風險組 → `/device-check`，只走受影響的情境
     5. 拿掉等待標記
3. **補走後段**：答案回來時已經過了第 4 或第 5 步 → 受影響的部分重跑第 4 步的審查與實機、第 5 步的回歸；交付文件已經產出的，重跑第 6 步。

完成條件：這題的等待標記全部拿掉（用題名搜 code、測試、規格、交付資料夾，結果是 0 筆）；答案不同時，受影響的測試先紅後綠、做過突變，該重跑的後段步驟都有新的結果。

`grill-me`、`to-questionnaire` 只能由使用者打指令叫。`grill-me` 只是叫 `grilling` 的捷徑，`grilling` 這裡叫得到，所以第 1 步遇到還沒定的決策時直接叫 `grilling`；`to-questionnaire` 沒有替代，只在「提醒」段提醒。

## 判斷目前進度（只讀）

1. **找工作目標**：候選是 feature-doc（`{DOC_DIR}/*.md`，見共用約定「規格來源」）。
   - 用目前分支名比對候選名稱（feature-doc 檔名，不分大小寫），剛好對上一個 → 就是目標
   - 對上好幾個 → 列出對上的，問使用者
   - 都對不上 → 候選只有一個就用它；有好幾個就列出來問使用者
   - 沒有候選 → 停在第 1 步，下一步 `/feature-doc`；設計還沒收斂就先 `grilling`
2. **讀證據**：
   - 任務：feature-doc 驗證紀錄表的狀態、第一個沒完成的 Slice、每個 Slice 有沒有標「高風險」和列出情境
   - 測試存在：狀態標 ✅、驗證方式寫 `unit test: 類別#方法` 的情境，在專案搜尋這個類別和方法（只搜尋，不跑測試）
   - 交付資料夾：`device-check.md`、`spec-review.md`、`regression.md`、`<主題>.html` 有沒有；第一行的 commit 是不是目前的 HEAD；`spec-review.md` 有沒有還沒閉合的必修
   - git：目前分支、未提交改動、最後一個 commit
   - 架構測試：專案有沒有（`regression.md` 第 5 項寫「這個專案沒有架構檢查」，或專案的測試裡找不到檢查依賴方向的測試）
   - feature-doc 結構（用 feature-doc 時）：每條 Requirement 至少一條情境；行為規格的每條情境在驗證紀錄表都有一列、名稱一致；寫 TODO 的情境狀態是 ⏸️ blocked
   - 還沒定與等外部：
     - 還沒定的決策：feature-doc 寫 TODO 的情境
     - 要 PM／後端回答的項目：feature-doc 待辦表「屬於誰」是 PM 或後端的列
     - 問卷：交付資料夾與 repo 根目錄的 `to-questionnaire-*.md`，各涵蓋哪些項目
     - 延後的題：標了「延後」的題，再問條件是什麼、成立了沒
     - 等待標記：專案 CLAUDE.md 宣告的等待標記（例如 `TODO(等PM)`）在 code 裡各有幾處
     - 答案回來、還沒處理：問卷裡已經有答案、code 還留著它的等待標記的題
3. **對照流程**：
   - 有答案回來、還沒處理的題 → 下一步是「問卷答案回來時」，排在下面所有規則前面（不處理就是照著已知錯的需求往下做）
   - 第 1 步還沒完成時，下一步依情況：
     - feature-doc 有 TODO 情境，且實作計畫的 slice 全是「未開始」→ `grilling`，範圍是待辦表「屬於誰」為使用者或 App 的 TODO 情境；屬於 PM／後端的只在提醒段提醒出問卷
     - 有組沒標「高風險」或沒列情境 → 第 1 步，列出哪幾組缺什麼
     - 已經開始實作後才有的 TODO 情境 → 照下面的規則判斷下一步，TODO 只列在提醒段
   - feature-doc 有 Requirement 沒有情境 → 第 1 步標「不確定」；有情境在驗證紀錄表缺列或名稱不同 → 第 2 步標「不確定」。兩種都在依據寫出是哪幾條
   - 標 ✅ 的情境在專案裡找不到對應測試 → 第 2 步標「不確定」，依據寫缺哪個測試
   - 審查閉合後又改了 code →「第 4 步之後又改 code」。判斷方式：HEAD 不是 `spec-review.md` 第一行的閉合 commit，或工作區有變動時，列出變動的檔案（`git diff --name-only <閉合 commit>` 加上 `git ls-files --others --exclude-standard` 的未追蹤新檔），扣掉 `spec-review.md`「排除」那行的檔案，再分類：
     - code、測試、資源、建置設定，或規格文件（feature-doc）→ 算改了，走「第 4 步之後又改 code」
     - 其他（筆記、跟這次無關的文件）→ 不觸發重審，只在提醒段列出
     - 分不出來 → 標「不確定」，列出是哪些檔
   - 任務沒做完 → 第 2 步；剛做完的組標了高風險、後面還有這次要做的組、`device-check.md` 裡沒有它 → 第 3 步
   - 任務做完，第 4 步的通過條件不成立（沒有 `spec-review.md`、必修沒閉合、實機沒涵蓋全部情境、有發現的處置還沒完成）→ 第 4 步
   - 沒有 `regression.md`，或它第一行的 commit 不是目前的 HEAD，或有程式檔比它新，或第 5 步的通過條件不成立 → 第 5 步
   - 沒有交付文件，或它的 commit 比 HEAD 舊 → 第 6 步
   - 前面都齊 → 第 7 步

## 輸出

```
下一步：<一個指令>，<為什麼>（判斷結果是「不確定」時改寫「請確認：<缺什麼、可能的原因>」）
<專案> · <feature 名稱> · 分支 <branch>
✓ 1 規劃        <依據>
→ 2 實作＋測試   <14/20，第 3 組未完成>
  3 實機        <第 2 組改到返回，device-check.md 沒有這組>
  ...
提醒：
- 還沒定：<情境或題號＋題目名稱>（影響：<範圍>）→ grill-me
- 要問 PM／後端、問卷裡還沒有：<項目> → to-questionnaire，請它存到交付資料夾
- 延後問 PM／後端：<題號＋題目名稱>（再問：<條件>）
- 等外部：等 PM <N> 處、等後端 <N> 處（細節用 /blocked）
- feature-doc 對不上：<哪條情境、缺什麼>
- 測試找不到：<情境＋測試名稱>
- 沒有架構測試 → /arch-test 可以建立
- 順便驗證：<回饋候選的規則>（這次會走到 <情境>）
```

提醒段照下表，只列讀到的項目，一項都沒有就省略。等外部的提醒不改「下一步」：開發照流程用暫定答案往下做。

| 讀到 | 提醒 |
|---|---|
| feature-doc 寫 TODO、屬於使用者或 App 的情境 | 要現在決定就打 grill-me（屬於 PM／後端的走下面「要問 PM／後端」那列） |
| 要 PM／後端回答、問卷裡還沒有的項目 | 打 to-questionnaire，請它存到交付資料夾 |
| 標了「延後」的題 | 只列題號與再問條件，不催出問卷。再問條件成立、或下一步是第 4 步時，改列進上一列，並問使用者要不要現在出問卷（過了第 4 步，答案跟暫定不同時審查、實機、回歸都要部分重跑） |
| 問卷已經涵蓋、code 裡還有等待標記 | 「等 PM <N> 處」這類計數，附「細節用 /blocked」；分類（其實已經可以做、還在等）交給 `/blocked` |
| 問卷在 repo 根目錄 | 提醒搬到交付資料夾 |
| 答案回來、還沒處理的題 | 列題目名稱與「跟暫定一樣／不同」，處理方式見「問卷答案回來時」 |
| 標 ✅ 的情境在專案裡找不到對應測試 | 列情境與測試名稱，確認前第 2 步維持「不確定」 |
| 專案沒有架構測試 | 「`/arch-test` 可以建立」，使用者說過這個專案先不建就不再列 |
| 有架構測試，但專案 CLAUDE.md 沒有「架構測試指令：`…`」那一行 | 「commit 前不會自動跑架構測試，`/arch-test` 第 4 步可以宣告」 |
| 回饋候選有「待驗證」的列，這次功能會碰到那個情境 | 列規則與會走到的情境；第 7 步更新驗證結果 |

完成條件：每一步都有狀態和依據（哪個檔、哪個數字）；判斷不了的標「不確定」並說缺什麼；「下一步」恰好一個指令，判斷結果是「不確定」時改寫「請確認：<缺什麼、可能的原因>」，不給指令；讀到的還沒定、等外部、feature-doc 對不上的項目都列在提醒段。

## 使用者說「繼續流程」時

判斷完進度後，直接叫下一步的 skill（`grilling`、`/device-check`、`/spec-review`、`/delivery-doc`、`/unit-test` 等）。一次只接一步，做完回到這裡重新判斷。

下一步屬於下面這幾種時，改成提醒使用者，由使用者決定：

- 只有使用者能叫的：`to-questionnaire`
- 要使用者授權的：commit、push、開 MR、問卷答案跟暫定不同時改測試的預期值
- 判斷結果是「不確定」的那一步
