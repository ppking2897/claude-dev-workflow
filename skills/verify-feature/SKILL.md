# verify-feature — 合併／rebase 後的規格核對

## 為什麼有這個 skill

合併一定伴隨解衝突，那是手動又容易錯的環節：某段邏輯被衝突解掉、兩邊的改動合錯、識別字改名改到一半。這些錯誤編譯不一定抓得到，但 code 已經不符合規格了。

這個 skill 只做一件事：**合併或 rebase、解完衝突後，確認 code 還是規格描述的那樣。**

涵蓋的情境：
- 把整合分支（develop 等）合進功能分支，取得最新
- 疊在別條分支上的功能分支，在底下那條更新後 rebase
- 把功能分支合進整合分支

## 不是什麼

- **不在開發當下跑**：驗證正在做的功能，是實作的一部分（unit-test 的事）
- **不是合併前的閘門**：它在合併**之後**跑
- **不審 code 邏輯對不對**，也不做架構檢查

## Step 0 — 認出這個專案的需求文件體系

| 看到 | 體系 | 規格在哪 | 驗證紀錄在哪 |
|---|---|---|---|
| `.claude/docs/*.md`，含驗證紀錄表 | feature-doc | 各 doc 的行為規格段 | doc 內的驗證紀錄表、`Verified` footer |
| 都沒有 | — | 問使用者規格在哪 | 沒有規格就只做 Step 1.2～1.3（看衝突怎麼解、有沒有殘留），並說明其餘無從核對 |

同時弄清楚：
- 整合分支叫什麼（develop、main……），看 git 分支與專案 CLAUDE.md
- 測試怎麼跑：跟 unit-test 的 Step 0 一樣，從專案既有的測試與建置設定推

## Step 1 — 確定範圍

### 1.1 這次帶進來了什麼

| 情境 | 取改動檔案 |
|---|---|
| 剛合併（有 merge commit） | `git log --merges -1` 取 merge commit → `git diff <merge>^1 <merge> --name-only` |
| 剛 rebase | `git diff ORIG_HEAD HEAD --name-only`（rebase 後 `ORIG_HEAD` 指向 rebase 前的頂端；不確定時從 `git reflog` 找） |
| 使用者指定範圍 | 照指定 |

### 1.2 衝突是怎麼解的

解衝突時手動改的部分最容易出錯，要逐段看有沒有邏輯被合掉：
- 合併：`git show --remerge-diff <merge>` 只顯示「解衝突時手動改了什麼」
- rebase：用 `git range-diff` 比對 rebase 前後同一串 commit，看自己的 commit 被改了什麼

### 1.3 衝突殘留

- 在改動檔案裡搜衝突標記殘留：行首的 `<<<<<<<`、`=======`、`>>>>>>>`

### 1.4 反查被波及的規格（只核對命中的）

從改動的檔案與識別字，找出受影響的規格。**只核對命中的，從不全部跑。**

| 優先 | 來源 | 作法 |
|---|---|---|
| 1 | 文件明列的涵蓋範圍 | feature-doc 的 `## 涵蓋範圍` 提到的檔案、型別、路徑 |
| 2 | 測試 | 改動的檔案被哪些測試涵蓋 → 那些測試對應的 Scenario（測試名稱、`// Scenario:` 這類註解） |
| 3 | 命名對應 | 功能資料夾名 ↔ doc 名稱（模糊比對） |
| 4 | 找不到 | 列出「動到 X，找不到對應規格」，請使用者指定或跳過 |

- **共用基礎設施**（基底類別、DI、路由、網路層）的改動波及很廣 → 不自動展開，列出來請使用者決定要核對哪些
- 印出範圍給使用者確認：「這次（<commit 或範圍>）波及 N 份規格：[...]」

## Step 2 — 對每份命中的規格做 readiness 檢查

### 2.1 測試

- 跑涵蓋這些規格的測試：先只跑相關的，最後整包再跑一次
- 綠 → ✅；紅 → ❌ drift：合併改壞了行為。修 code 還是改規格，由使用者決定

### 2.2 手測是否過期

- 靠實機或模擬器手測驗證的 Scenario（feature-doc 驗證紀錄表的日期）→ 那段 code 在驗證之後有沒有改動（含這次合併）→ 有就 ⚠️ stale，列出需要重測的
- 驗證方式寫實機紀錄編號的（例如 `device-check.md #6`）也算手測，即使沒寫「手測」兩個字；同時列了 unit test 的情境，測試綠了也不代表畫面還對，一樣要判斷手測過期

### 2.3 識別字對賬

- 從 doc 的 code block、`## 涵蓋範圍`、驗證紀錄表抽出提到的型別、函式、enum 值、測試類別 → 在 code 裡確認還存在；enum 或 sealed 類別的成員是否完整
- 找不到 → ❌ drift：解衝突把東西弄不見，或改名改到一半

### 2.4 規格內部一致

- feature-doc：Slice ↔ Requirement 對得上；驗證紀錄的 Scenario 名稱與行為規格一致

### 2.5 還沒 ready 的

- 未完成的 Slice、blocked 項目 → 🔲 列出。不是錯誤，是「你要知道的事」（可以直接用 blocked skill 列）

## Step 3 — 報告（直接印出，不寫檔）

```markdown
## Verify Report — {merge 或 rebase}：{commit／範圍} → {分支}
- 波及範圍：{N} 份規格 — {list}

### 整體判斷
{✅ 核對通過 / ⚠️ 有 caveats / ❌ 有 drift 要處理}

### {規格 A}
- ✅ 測試全綠（{x}/{y}）
- ⚠️ Scenario「X」手測過期（{日期} 驗，這次合併又改到）
- ❌ `FooBar` 在 doc 裡有，code 找不到 — 解衝突弄掉了？
- 🔲 還沒 ready：Scenario「Y」未驗證

### ❌ Drift（要處理）
### ⚠️ Caveats / Stale（你要知道）
### 🔲 還沒 ready
### 📝 這次帶進來的 commits
```

## Step 4 — 漂移分類（🤖 可以修 vs 🧑 你判斷）

| 分類 | 判定條件 | 例子 |
|---|---|---|
| 🤖 可以修（先問過使用者） | code 是正本、文件只是**描述**錯，不涉及行為契約 | 檔名寫錯、有一對一 diff 證據的明顯改名、驗證紀錄的 Scenario 名稱不同步 |
| 🧑 使用者判斷 | 行為契約改動 | enum 成員增減、API path、state 欄位、event 名稱——可能是規格被改壞 |
| 🧑 使用者判斷 | 測試變紅 | 合併改壞了行為——修 code 還是改規格？ |
| 🧑 使用者判斷 | 識別字消失 | 解衝突把東西弄不見——補回來還是文件刪掉？ |
| 🧑 使用者判斷 | 手測過期 | 要重測嗎？哪些優先？ |

原則：
- code 是正本、文件寫錯 → 可以修文件
- 規格是契約、code 沒做到或被改壞 → 使用者決定
- 兩邊都不確定 → 使用者決定

自動修只動文件、不動 code。**行為規格是契約，一律不自動修**；技術設計的描述性錯誤才屬於可修範圍，而且要先問。

## Step 5 — 留紀錄（依體系）

- **feature-doc**：使用者確認報告都處理完後，更新 footer `**Verified**: YYYY-MM-DD @ <short sha>`（sha 取 `git rev-parse --short HEAD`；只有這個 skill 寫 footer）
- 還有未完成或 blocked 的項目不阻擋留紀錄——這是「規格與 code 對齊」的聲明，不是「全部做完」的聲明

## 原則

- **報告，不硬擋**：合併已經發生，要不要修由使用者決定
- 不自動改 code、不自動寫測試
- 只核對被波及的規格
- 報告要具體：規格名 + Scenario + 期望 vs 實際

## 與其他 skill 的關係

- **unit-test**：它寫的測試，就是 2.1 跑的東西
- **blocked**：2.5 的「還沒 ready」可以直接用它列
