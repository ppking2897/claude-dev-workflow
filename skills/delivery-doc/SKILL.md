# delivery-doc — 交付文件

交付資料夾、規格來源、subagent 分段見 `~/.claude/skills/my-flow/conventions.md`。

時機：審查閉合、回歸測試通過之後，開 MR 之前。輸出 `<交付資料夾>/<主題>.html`，圖片用相對路徑引用 `device/`、`target/`，不重拍。

順序：先跑 `/blocked`（第 8 段要用）→ 寫下面八段 → 「核對」。

## 內容（依序）

1. **現況**：白話一段，說做了什麼、能不能交、還差什麼。
2. **流程圖**：這次改動到的使用者流程（Mermaid flowchart）。
3. **UML**：改動到的類別與呼叫（classDiagram 或 sequenceDiagram），只畫改動和直接相關的部分。
4. **改動處**：淺層檔案樹，每個檔案一行職責，標新增／修改／刪除。
5. **實機對照**：實機與要實現的畫面並排，附 `device-check.md` 列的畫面差異與數值差異。
6. **情境對證據**：情境｜驗證方式｜證據（測試名稱或截圖）｜日期｜結果。
7. **檢查紀錄**：彙整 `device-check.md`、`spec-review.md`、`regression.md` 的檢查紀錄，以及 `/unit-test` 的改壞結果（位置見共用約定）：各抓到什麼、花多久。數字從各份紀錄的明細重數，不抄統計列；跟統計列對不上時，連來源檔一起修。表末加一列「交付文件核對」，核對做完再填：日期、花多久、對不上幾處、來源檔錯幾處；重跑這一步時保留舊的列。
8. **還沒做與等外部**：跑 `/blocked`，放它的清點結果（其實已經可以做、等外部、卡在其他任務、清單與 code 對不上），等外部的每項附移除條件，照抄 feature-doc 待辦表的「移除條件」欄或 code 的等待標記。

某段不適用時寫一行理由，不留空白。Mermaid 用 CDN 載入並鎖定版本；寫在 HTML 裡的 `<<interface>>` 這類標註要寫成 `&lt;&lt;interface&gt;&gt;`，不然瀏覽器會把它當成 HTML 標籤吃掉、整張圖報語法錯誤。

每句事實（時間、數字、截圖、「後端會／不會送什麼」這類行為描述）都要指得出來源：紀錄檔的哪一列、截圖檔名與檔案時間、指令輸出、code 的檔案與行號。指不出來就照實寫「沒記」「這輪沒有截圖」「程式沒有規定」，不估、不補。寫初稿和修正時都一樣，修正時最容易為了把空格補完整而憑印象填。

## 核對

寫完後照共用約定分段派 subagent（最多 5 個；流程圖、UML、改動處三段要互相對得上，交給同一個）。每個 subagent 唯讀、effort 設 `xhigh`，比對自己那幾段跟 code、截圖、`spec-review.md`，列出對不上的地方，以及找不到來源的句子。

主對話只修文件。核對中發現的 code 問題列出來交給使用者，不在這一步改 code。修正超過 5 處時，請列出那些不一致的同一個 subagent 只看修正處。複查最多 3 輪，第 3 輪還有不一致就停下來交給使用者（見共用約定「subagent 分段」）。

修完後用瀏覽器打開 HTML，確認每張 Mermaid 圖和每張圖片都畫得出來。Chrome 擴充功能開不了 `file://`，改用 `127.0.0.1` 起本機伺服器開。

完成條件：8 段都有內容或寫明不適用的理由；核對列出的不一致都已修正或附理由保留，修正超過 5 處的已經複查；第 7 段有這次核對的一列；瀏覽器裡 Mermaid 圖和圖片都畫得出來；回報 HTML 的完整路徑。
